# SupportOps 系统评审与完善建议

评审日期：2026-09-29。本文基于当前工作区源码、接口、持续集成配置及已有验收记录，评估下一阶段投入方向。建议先完善现有能力，再以一个真实只读接入验证可迁移性。

## 评审范围与证据时效

- 覆盖诊断执行、MCP、知识处理与检索、项目记忆、模型配置、账号权限、飞书、评测中心、受控修复、前端交互、测试及运行方式。
- 本次重新执行 JavaScript 回归：82 项通过，0 失败、0 跳过。
- 本次未重新运行 Java 全量测试、浏览器业务流程或真实模型实验。检查时 18092、19196 两个已知本地应用端口均未响应；端口未运行本身不判定为系统缺陷。
- [9 月 28 日独立复验](../controlled-remediation-independent-reacceptance-20260928.md)及[9 月 26 日真实服务验收](../real-provider-acceptance-20260926.md)属于历史证据，不能等同于本次重验。
- 这是一轮系统评审，不构成完整安全审计、负载测试或生产就绪认证。

## 总体判断

系统已有较完整的功能组合：持久化诊断与流式恢复、带版本和来源的检索、隔离评测、审批约束下的固定修复、未知结果保守处理，以及基础身份与渠道接入。下一阶段的主要不足是效果证据、实际业务结果沉淀、可复现交付和真实目标适配，而非功能入口数量。

建议近期约 70%–80% 的精力用于完善与验证，剩余精力用于真实只读接入的需求梳理和小范围验证。该比例是投入建议，不是工期估算。多 Agent、技能市场、完整工单平台和微服务拆分暂不作为主线。

## 发现与优先级

### SR-01：崩溃恢复测试与 Linux 持续集成不兼容

**性质：具体代码问题；优先级：下一次交付前修复。**

[持续集成配置](../../.github/workflows/verify.yml)使用 `ubuntu-latest` 和 Temurin JDK 21 执行 Maven `verify`。但 [RemediationPersistenceTest](../../src/test/java/io/supportops/remediation/RemediationPersistenceTest.java) 第 541 行固定使用 `bin/java.exe` 启动子 JVM，没有按操作系统选择可执行文件。标准 Linux JDK 使用 `bin/java`，因此该测试在当前 CI 配置下会在启动子进程时失败。本次未执行 Linux CI，结论来自代码路径与执行环境的直接冲突。

建议复用已有评测测试中的跨平台处理方式，并在 Windows 与 Linux 验证真正的子进程退出及恢复断言。不能通过跳过 Linux 测试来规避问题。CI 已经存在，完善重点是保证新增测试与其实际环境一致。

### SR-02：评测中心具备运行能力，质量基线仍不充分

**性质：证据缺口；优先级：高。**

当前评测集仅支持登记内置六场景，不支持独立案例集导入。真实服务验收仅覆盖一个对话路由、一个嵌入模型、一个检索策略，每场景运行一次。辅助证据审阅为五例通过、一例证据不足，评测中心人工审阅覆盖率为 0/6，不能据此得出稳定准确率。

文档注入案例的关键攻击片段未进入实际检索结果，因此尚未覆盖完整攻击暴露条件。也没有同一资料与问题下的重复策略对照，无法证明混合检索或 ONNX 重排序带来的收益。参见[评测边界](../evaluation-center.md)与[真实服务验收](../real-provider-acceptance-20260926.md)。

建议先形成 20–30 个经过人工确认的案例，覆盖相似症状不同根因、证据缺失、矛盾材料、旧版本、服务超时和文档干扰。开发案例与保留测试案例分开；先比较关键词与混合检索，每例至少重复三次，固定资料、模型配置和检索预算。ONNX 待其环境与稳定性验证完成后加入比较。

人工确认标准应包含必要事实、允许的不确定性、禁止结论和引用要求。具备稳定的检索相关性标注后，再报告 Recall@K 等指标；此前使用已有结构检查和人工维度。攻击验证应在原检索预算内构造可确认暴露的案例，不以扩大候选或返回数量获得表面通过。

### SR-03：诊断记录到实际解决结果缺少通用关联

**性质：现有流程完善；优先级：高。**

诊断任务状态、修复执行及业务验证、评测人工审阅都有各自记录，但目前未发现面向所有诊断的结构化处理结果回填，以及经人员确认后转入评测集的通用流程。仅依据任务完成状态或修复执行成功，无法统计建议是否帮助用户解决问题。

建议增加轻量结果记录：已解决、部分解决、未解决、无法确认；关联采取的措施、证据和确认人，并保留修改历史。修复结果可以作为证据来源，但不能自动等同于所有业务问题已解决。案例进入评测集前，明确确认、脱敏、冻结资料与预期标准；不自动将对话或模型结论变成标准答案。

验收重点是记录归属、权限、版本冲突、历史可追溯和人工确认。此范围无需引入指派、排班、SLA 等完整工单能力。

### SR-04：真实场景适配仍受内置目标约束

**性质：当前设计边界；优先级：完成核心完善后的首选扩展。**

[AgentScopeEngine](../../src/main/java/io/supportops/agent/service/impl/AgentScopeEngine.java)直接依赖 `DemoService`，由 `demo.appInfo().version()` 确定检索版本，并连接内置 OrderBridge MCP。受控修复也仅支持内置目标的固定路径迁移。因此，上传其他业务文档并不等于已经支持其他 Java 服务。

建议只接入一个可控的外部 Java 测试服务，先支持应用身份与版本、脱敏配置摘要、限定日志和健康状态读取。目标由管理员在服务端登记，凭据按目标隔离；调用具有明确超时、返回大小和目标边界。诊断、版本过滤、证据和评测必须绑定同一个目标。

验收应以该服务产生的真实 HTTP、日志和版本事实为依据，验证版本切换、不可达、超时和凭据错误。外部写操作、通用脚本、任意 SQL 和连接器市场不包含在该扩展中。

### SR-05：回答可读性、延迟与用量尚需共同优化

**性质：历史测量揭示的改进方向；优先级：高，与质量基线共同推进。**

9 月 26 日六次真实诊断平均耗时 76.428 秒，回答长度 5254–6685 字符，累计报告对话用量 108,785 Token，且未覆盖嵌入用量。样本少、路由单一，这些数字不能作为生产性能基准或全部费用，但足以支持进一步检查重复工具读取、重复引用和回答长度。

建议默认先呈现结论、关键证据、处理步骤与尚缺信息，完整工具与检索证据可展开。分别记录准备、首段可见输出、工具、模型和总耗时；展示计量覆盖范围，不把未报告的用量当作零。以固定案例对照改进前后质量、延迟和用量，不以丢弃证据换取更短答案。

### SR-06：自动化验证应覆盖真实页面与交付环境

**性质：验证与运行体验完善；优先级：高。**

现有 CI 包括 JavaScript 测试、真实隔离存储下的 Java 验证与六场景源检查。页面刷新、回执恢复和审批执行已有人工浏览器验收证据，但工作流中未发现自动浏览器端到端回归步骤。脚本状态测试能够保护部分语义，仍无法覆盖完整页面绑定与真实导航。

建议优先自动化少量高价值流程：刷新后原请求恢复、响应丢失后的只读核查、登录身份切换、配置版本冲突、评测复制后的重新预检，以及审批失效后禁止执行。

运行体验同时补齐依赖检查、实例与程序版本识别、故障定位入口和备份恢复演练。启动状态应能区分存储不可达、模型未配置、端口占用和已有实例；诊断输出不得包含凭据。用独立目录与数据库验证启动、迁移和恢复，保护当前工作台数据。

### SR-07：维护成本需要按业务职责控制

**性质：维护风险；优先级：随相关功能完善实施。**

`app.js` 同时承担身份、导航、诊断、配置、用量和账号交互；文档处理、评测及修复服务也承担较多流程职责。规模本身不能证明存在缺陷，但后续继续叠加功能容易扩大修改影响面。

建议按业务页面分离前端协调逻辑，后端按事务、状态转换和外部调用边界提取职责明确的组件。请求冻结和未知结果恢复逻辑须保留各自契约，不机械合并。先用现有回归与必要的契约测试保护行为，再进行局部调整；无需更换前端框架或拆成微服务。

### SR-08：团队化能力应在多人使用前补齐

**性质：使用规模边界；优先级：取决于部署目标。**

当前有 ADMIN/USER、记录归属和基础访问控制，但 [UserController](../../src/main/java/io/supportops/user/controller/UserController.java)仅提供初始化、登录、退出、列表和创建，没有账号停用或密码重置入口。诊断与环境操作使用全局运行准入，项目记忆及目标也以单环境为基础。

个人演示阶段可保留这些边界。若要给团队持续使用，应先补账号生命周期，再根据实际项目隔离要求设计资源归属和目标级并发。不能只移除当前全局互斥来提高并发，否则可能破坏诊断与修复的环境一致性。此项不等同于要求立即建设完整 RBAC 或多租户平台。

## 建议开发顺序及完成条件

| 阶段 | 具体工作 | 完成条件 |
| --- | --- | --- |
| 1. 交付可靠性 | 修复跨平台测试；补关键页面自动回归；完善运行状态与恢复说明 | Windows/Linux 相关检查通过；刷新、身份切换、响应丢失不会重复写入；隔离启动和恢复可复现 |
| 2. 质量与处理结果 | 轻量结果回填；受控案例登记；人工基线与重复对照；回答和用量改进 | 处理结果有确认人与证据；案例不可变且脱敏；开发与保留集分离；报告质量、失败、延迟和用量，不只展示成功案例 |
| 3. 真实场景迁移 | 单个外部 Java 服务的只读适配 | 同一诊断链可用于外部服务；目标和版本一致；真实失败可定位；沿用上述质量与恢复验证 |

局部模块拆分随阶段 1、2 的实际改动推进，避免独立进行大范围重构。账号生命周期在团队试用前完成。每个阶段的对外介绍都应区分实现、测试和真实业务效果。

## 展示价值

下一轮最有说服力的交付是一个可复现案例：真实异常产生现场证据，诊断引用适用资料，人员确认处理方案，处理后留下验证与结果记录，最后成为可重复评测案例。配套展示改进前后的质量、耗时和用量，以及响应丢失、旧版本和证据不足时系统如何处理。

这条案例能够解释现有持久化、权限、检索、审批与评测机制各自解决什么问题，并为后续扩展提供依据。
