## 1. 执行约定

- 只实现本次 V1：内置 OrderBridge 固定配置迁移、人工审批、执行后验证、审计与恢复。后续扩展不自动开发。
- 按依赖完成实现、必要修复和复验；任务编号不是逐项等待批准的停点。内部类名、普通布局及实现细节可自主决定。
- 先读取根 `AGENTS.md`、两份规划及实际相关源码，检查 Git 状态。保留现有评测中心、真实模型验收文档和其他未提交改动。
- 仅当源码变化使授权、数据兼容或核心状态语义无法成立时说明具体冲突和替代方案；不要将普通技术取舍升级为再次确认。
- 不提交、推送、发布，不替换用户正在查看的工作台。隔离验收完成后，更新日常实例是独立部署动作。
- 本功能不需要真实模型调用，也不把历史模型调用授权或现有凭据当成调用新端点的依据。
- 使用 JDK 21 和仓库 Maven Wrapper；共享 `target/` 的构建必须串行。Java 显式类型、中文 Javadoc、MyBatis-Plus、GET/POST 和中文 OpenAPI 遵循根规范。
- 测试使用经过核对的独立数据库、回环端口、运行目录；真实 MySQL 与本地下游 HTTP 不能用内存数据库和返回预设成功的桩替代。
- 本次规划未启动或停止服务。执行者须现场核对监听、存储归属与活动任务，不能将规划时端口当作空闲证明。

## 3. 开发任务

### CR-01：定义契约与固定范围

入口：`DemoController`、`DemoEnvironment`、`DemoService`、`RunService`、`UserAccessFilter`、`CurrentUser`、`docs/api.md`、`docs/users.md`。

开发工作：

1. 定义固定 actionId、动作版本、验证版本、提案 schemaVersion 和审批策略版本。
2. 定义 preview、不可变 plan、decision、execution、receipt、verification、event、request 的明确类型。
3. 固定状态转换和错误码；特别分清 APPLIED、VERIFICATION_FAILED、UNKNOWN、CLOSED_UNRESOLVED。
4. 定义 planHash 的规范化方式、固定请求协议、有效期、超时、证据大小限制。
5. 标明旧 `/api/demo/repair-config` 的兼容收紧及场景构造接口的例外，不留下隐藏无审批执行路径。
6. 验证依赖方向，避免 remediation 与 demo/agent 服务之间形成循环。

验收：规范中没有任意命令、目标地址或模型授权字段；单管理员审批不被描述为双人复核；所列状态均有进入条件、允许动作和恢复方式。

### CR-02：数据层、事务和增量升级

入口：新 `src/main/java/io/supportops/remediation/`、`src/main/resources/mapper/remediation/`、下一号 Flyway 迁移、现有持久化测试工具。

开发工作：

1. 创建 plans、decisions、executions、requests、events 五类表，补齐长度、空值、外键、索引和排序规则。
2. 提案一决策、一执行；operationId 唯一；操作者 + requestId 唯一；同请求不同摘要冲突。
3. 明确受理和完成事务，状态/证据/事件同事务提交；条件更新检查影响行数。
4. 审计采用追加方式，核查及人工结束保留原失败/不明事实。
5. 实现服务端分页与游标事件查询；报告读取已保存证据。
6. 核对现有 V8 数据升级及 `EvaluationMigrationTest` 的迁移次数断言，按真实版本更新，不删历史数据保护断言。

验收：隔离 MySQL 验证空库初始化、V8→新版本、旧诊断/事件/账号/评测/审阅保持一致；唯一约束、事务回滚、分页、并发更新用独立 JDBC 查询核对。已应用迁移不改写。

### CR-03：拆分示例应用与验证，建立可靠回执

入口：`demo/service/DemoService.java`、`demo/service/impl/DemoEnvironment.java`、demo DTO/VO 及新增受控适配器。

开发工作：

1. 引入 instanceId 和单调环境 revision；配置、场景和故障条件变化均更新，读操作与普通日志追加不更新。
2. preview 返回真实配置与适用性，不发订单请求，不以场景标签替代现场判断。
3. 实现确定性配置变换，保留无关配置；动作内原子校验实例、修订和 before。
4. 将“应用配置”和“业务验证”分开；记录 operationId、应用前后修订和固定验证 requestId。
5. 每 execution 最多一次应用和一次业务验证；响应至少验证 HTTP 200、accepted=true、路径及配置读回。
6. 建立有界内存回执与在途登记；只读查询原回执不产生新的同步请求。重启不假装保留回执。
7. 仍保留真实回环 HTTP 下游，不把诊断结果、场景期望值或硬编码成功用作验证结果。

验收：实际 HTTP 410→配置变更→新请求 200/accepted=true；无关配置保留；healthy/credentials/unavailable/未知版本不能误套动作；重复 operationId 不增加写入或请求次数；旧请求成功和健康检查 200 不能通过验证。

### CR-04：不可变提案、人工审批与撤销

入口：新 remediation service/DTO/VO、UserService、RunService 的诊断读取入口。

开发工作：

1. 从当前服务端现场生成提案，支持可选已结束诊断关联；缺失或不合法来源明确拒绝。
2. 保存不可变内容、planHash、创建人及有效期；复制必须重新获取现场，不复制旧审批。
3. approve/reject/cancel 实现固定请求幂等和 expectedVersion 检查。
4. 批准时绑定完整动作与目标快照；执行时再次检查批准人和执行人的有效 ADMIN 身份。
5. 处理过期、环境变化、动作版本变化及实例重启，禁止旧提案复活。
6. 批准不自动执行；撤销与执行受理竞争时以数据库条件更新确定唯一胜者。

验收：正文篡改、过期、改配置后改回、同名场景重置、另一实例、撤销、驳回、伪造审批人均不产生应用；两个标签页同时审批的记录与事件一致；同人提案/审批按 V1 政策可用且真实记名。

### CR-05：执行、幂等、结果不明与恢复

入口：RemediationService、受控 adapter、RunService.whenIdle、事务与应用生命周期恢复组件。

开发工作：

1. 在共享准入边界内完成最终检查、审批消费、受理落库、应用与验证；不把外部 HTTP 放入长数据库事务。
2. 固定请求查询优先于“审批已消费”判断；同一提案从不同入口/不同 requestId 并发执行也只有一次。
3. 应用与验证证据原子落库，准确区分未应用、验证失败和结果不明，保留固定操作身份。
4. 响应丢失、处理器异常、数据库完成事务失败时不生成替代写入；同实例从原回执补录。
5. 保存实例与进程启动身份，启动恢复只对确认退出的旧执行标记待核查，不接续旧写入；进程身份不明或跨实例缺失回执时继续 UNKNOWN，不凭超时抢占。
6. 核查原操作，无新增配置修改和业务 POST；在途状态下拒绝人工结束或抢占。
7. 人工结束未决记录要求理由、有效身份与退出证据；保留 UNKNOWN 事实。后续重提关联原执行，重新审批。
8. 同一目标有未决执行时阻止新修复；示例重置和刷新不能清除该约束。

验收：并发及故障注入能证明应用次数、验证 POST 次数和执行行数；进程在受理后、应用后及验证后退出均不自动重跑；缺证据不能变绿。401/503/accepted=false 使用真实 HTTP 故障路径；故障测试钩子只在测试中启用。

### CR-06：API、权限和旧入口治理

入口：新 RemediationController、DemoController、UserAccessFilter 回归、统一异常与 OpenAPI。

开发工作：

1. 实现设计中的动作/预检查/提案/审批/执行/请求查询/核查/报告接口，全部使用 GET/POST。
2. 所有新接口管理员校验，POST 头与来源检查；服务端捕获 actor，不信任正文身份。
3. 旧 repair-config 路径委托同一服务，无审批请求 409 且无配置或同步副作用。
4. 场景构造和独立同步保留现有权限/诊断互斥；增加环境变化记录，不串用验证结果。
5. 统一有界参数、稳定错误码、版本冲突、请求内容冲突及权限说明。
6. 提供中文 Tag/Operation/Schema/响应说明，核对生成的 OpenAPI 引用与实际请求必填项。

验收：未登录 401、USER 403、缺 POST 头 403、GET 不写入；管理员不能用伪造字段/旧入口绕过审批；新旧执行入口共享幂等结果；日志/API/报告不含真实密码或 Authorization。

### CR-07：修复中心及页面恢复

入口：新 `static/remediation.js`、`remediation.css`，小范围接入 `app.js`、`index.html` 和诊断详情。

开发工作：

1. 列表、详情、新建、差异、批准/驳回、撤销、执行、证据、审计与导出完整可用。

6. 复用现有文本/Markdown 安全渲染，处理键盘焦点、反馈播报和窄屏阅读。

验收：真实浏览器完成成功、驳回、撤销、过期、环境变化、响应丢失、刷新恢复和待核查流程；USER 页面无入口且直调仍被拒绝。新增 JS 测试关注固定请求与恢复逻辑，不只匹配 HTML 字符串。

## 4. 必测验收矩阵

| 编号 | 场景 | 必须证明 |
| --- | --- | --- |
| R01 | 迁移故障完整闭环 | 原请求 410；批准；只应用一次；新请求 200/accepted=true；差异与审计入库 |
| R02 | 预检查和创建提案 | 没有配置变化、业务 POST 或模型调用 |
| R03 | 不适用动作 | 健康/凭据/下游故障及未知版本不会被错误配置动作覆盖 |
| R04 | 无审批与越权 | 未登录、USER、缺请求头、旧直通入口都不写入 |
| R05 | 篡改绑定 | 参数/planHash/版本/目标/审批人伪造被拒绝 |
| R06 | 环境漂移 | 场景同名重置、配置改回原值、实例重启仍使旧审批失效 |
| R07 | 批准、驳回、撤销、过期 | 不自动执行；过期/撤销/驳回不能消费；竞争只有一方成功 |
| R08 | 重复与并发 | 同请求重放、不同请求同时执行、新旧入口交叉调用仅一执行、一次应用、一次验证 |
| R09 | 请求编号冲突 | 同编号不同正文/目标稳定冲突，不覆盖旧请求 |
| R10 | 诊断与人工操作竞争 | 活跃诊断禁止修复，修复期间禁止场景重置和新诊断穿插 |
| R11 | 应用后验证失败 | 401/503/accepted=false 保留 APPLIED 与验证失败，不声称未修改或恢复 |
| R12 | 验证证据不足 | 健康检查 200、历史请求成功、无回执当前配置正确均不能确认本次成功 |
| R13 | 响应丢失与刷新 | 使用原请求身份查询；客户端不新建写入；重登按账号隔离 |
| R14 | 受理/完成事务故障 | 前置落库失败零写入；应用后落库失败可读原回执补录且不再发 POST |
| R15 | 进程中断与重启 | 受理后/应用后/验证后中断均不自动重跑，缺证据保持 UNKNOWN |
| R16 | UNKNOWN 处理 | 核查不重发；在途不能人工结束；结束未决仍保留 UNKNOWN；新提案重新审批 |
| R17 | 迟到结果与资源限制 | 迟到结果不覆盖合法终态；回执缓存/证据超限不静默丢失后判成功 |
| R18 | 增量数据库迁移 | V8 原诊断、账号、评测及审阅保留；约束、事务、排序分页真实 MySQL 验证 |
| R19 | 浏览器与输入安全 | 全闭环、窄屏/键盘、恶意文本安全显示、恢复记录不跨账号 |
| R20 | 报告与全量回归 | 报告关联实际证据；OpenAPI 可用；Java/JS 通过；原诊断/评测语义保持 |

有些负例需要在配置迁移后控制下游返回异常。应使用测试专用受控故障注入或隔离 HTTP 服务；不能为通过用例在生产接口开放任意地址或故障参数，也不能在审批后调用会使 revision 变化的场景接口，再将被拒绝的执行当作“验证失败”证据。
