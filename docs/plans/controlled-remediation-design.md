# 受控修复、人工审批与执行后验证：V1 设计

状态：2026-09-27 已完成 V1 实现，以及独立复验发现的输入恢复、正文超时、场景审计三项补修；逐项当前结果见 [补修与隔离复验](../controlled-remediation-fixes-acceptance-20260927.md)。[首次验收](../controlled-remediation-acceptance-20260927.md) 保留为历史证据。本文保留 2026-09-26 制定的范围和契约；不代表真实系统修复授权或生产可用性证明。

配套文档：[开发任务与验收清单](controlled-remediation-tasks.md)。现有边界见 [架构说明](../architecture.md)、[用户系统](../users.md) 和 [路线图](../../ROADMAP.md)。

## 1. 目标与首版范围

将“诊断后人工改配置”连接为可审阅、可追踪的处理流程：查看现场证据 → 生成明确的修复提案 → 人员审批 → 服务端重新校验并执行 → 用新的请求验证 → 保存结果与审计记录。

首版使用已有的 OrderBridge 本地示例环境，固定一个修复动作：将 2.0 版本的旧路径配置迁移到 `sync.targetPath=/v2/orders`。技术重点是授权绑定、条件更新、重复请求保护、环境变化检测和不确定结果核查。示例下游发生真实回环 HTTP 交互，但仍是合成环境，不代表真实订单系统或企业连接器验收。

### 1.1 V1 必须交付

- 管理员后台“修复中心”：列表、提案详情、审批、执行、结果、核查与审计。
- 从已结束的诊断进入创建提案；也可在修复中心独立创建。关联诊断是证据来源，不是执行授权。
- 服务端固定动作目录与只读预检查；展示配置前后差异、影响、验证方式及失败边界。
- 不可变提案、显式批准/驳回、撤销、审批有效期、环境变化后重新提案。
- 一次性审批消费、固定请求编号、幂等受理、诊断与修复互斥。
- 分开记录配置应用和业务验证；成功、验证失败、未应用、结果不明有不同语义。
- 进程重启、响应丢失、数据库落库失败后的保守核查；不自动重做配置写入或业务探针。
- 持久化证据与追加式审计，JSON / Markdown 报告。
- 真实隔离 MySQL、实际本地下游 HTTP、浏览器及权限验收。

### 1.2 明确边界

| 项目 | V1 决定 |
| --- | --- |
| 操作目标 | 当前实例内置 OrderBridge；目标由服务端注册，页面不传地址、数据库或文件路径 |
| 修复动作 | 仅固定的 2.0 路径配置迁移；不开放 Shell、SQL、脚本上传、任意 HTTP 或模型生成的命令 |
| 权限 | 沿用 ADMIN / USER；修复全部接口仅 ADMIN，USER 保持现有诊断能力 |
| 审批人数 | 单管理员显式审批，允许提案人与审批人相同；记录身份，不宣称双人复核 |
| 执行方式 | 人员点击执行；模型不能批准或执行，MCP 四个只读工具保持原有范围 |
| 调度 | 当前单进程本地环境内短时同步执行，不引入后台队列、定时修复或自动重试 |
| 多实例 | 不扩展共享业务环境的多节点执行；提案必须绑定实际实例身份，不得跨实例执行 |
| 回滚 | V1 不提供自动回滚；恢复旧配置仍是写操作，不能在失败后隐式执行 |
| 模型依赖 | 创建、审批、执行和验证不需要调用模型；诊断建议只是人员判断的参考 |
| 评测中心 | 保持现有诊断评测语义；修复回归由独立测试覆盖，不把新增修复指标混入原实验 |

首版直接保留真实系统适配所需的动作、前置条件、回执和验证契约；不提前建设通用工作流引擎、完整工单、多租户权限或连接器市场。

## 3. 页面与完整使用流程

### 3.1 修复列表

展示提案名称、固定动作、目标实例简称、关联诊断、提案人、审批人、创建时间、提案状态、执行结果与验证结果。分页默认 20、最多 100，支持状态筛选和稳定的时间/ID 排序；V1 不做物理删除。

从已结束诊断点击“创建修复提案”，只预填 `sourceRunId`。管理员选择固定动作并说明理由；服务端重新采集现场，不将诊断自然语言自动解析成执行参数。诊断已归档不删除其证据；修复关联不能恢复续聊或改变归属。

### 3.2 创建与审批

1. 展示当前配置、实际生效路径、应用版本、实例身份、环境修订及采集时间。
2. 展示服务端生成的前后差异、适用条件、修复范围、一次业务验证请求及失败处理。
3. 创建后冻结提案。需要修改理由、动作或参数时复制为新提案，重新采集现场和审批。
4. 审批页明确批准的是哪一份目标、参数和验证策略；批准和执行是两个独立动作。
5. 批准前再检查环境及提案有效期；驳回必须说明原因。已批准但未执行的提案可以撤销。
6. 提案有效期默认创建后 30 分钟；批准后可执行窗口为 10 分钟，且不能晚于提案截止时间。服务端时间为准。

页面不提供可自由编辑的配置键、路径、目标地址或验证 URL。模板变更后旧提案不能自动升级为新动作。

### 3.3 执行与结果

点击“执行已批准修复”后保留本次固定请求。执行通常数秒，页面可显示处理中，但不能凭按钮禁用防重。刷新或响应丢失后按请求编号查询服务端，不自动生成新编号。

详情分别显示：

- **配置应用**：是否确认写入、实际前后值、环境修订、操作回执。
- **执行后验证**：新请求的时间、路径、HTTP 状态、`accepted`、错误码及配置读回。
- **结论**：验证通过、已应用但验证未通过、确认未应用、结果待核查或人工结束未决记录。
- **审计**：谁在什么时间提交、批准、执行、撤销、核查，以及当时绑定的提案摘要。

结果不明时提供“核查原执行”。核查只读取回执、历史请求和现场；不重新应用配置、不重新发送业务 POST。缺少足够证据时继续显示不明，不能仅凭当前配置正确就归因于本次操作成功。

### 3.4 旧入口与示例操作

- “示例环境”的“应用 2.0 路径配置”改为“创建修复提案”，跳转修复中心。
- 保留 `POST /api/demo/repair-config` 路径作为过渡入口，但必须携带已批准提案及同样的执行请求字段，委托新服务完成。无审批旧请求返回 409 `REPAIR_APPROVAL_REQUIRED`，且零写入。这是明确的接口行为收紧，必须同步文档、页面和测试，不能保留隐藏直通分支。
- `/api/demo/scenario` 仍属于管理员构造合成场景的测试入口，可将环境重置为健康状态；它不是“经审批修复”的一部分。该入口必须更新环境修订、记录操作来源、使旧审批失效，并在修复期间拒绝执行。
- `/api/demo/sync` 是人员手动发送的独立示例请求。保留权限与互斥，不能将它的成功结果冒充某个修复执行的验证证据。
- 产品文档明确此演示边界，不宣称所有示例场景重置都受修复审批控制。

## 4. 固定动作与审批绑定

### 4.1 动作目录

首个动作 ID 建议 `ORDERBRIDGE_MIGRATE_SYNC_PATH`，动作版本 1，验证策略版本 1。动作由服务端静态注册，未来不同动作通过明确适配器扩展。

适用条件至少包括：目标为本实例注册的 OrderBridge，应用版本 2.0，提供配置中的旧键为 `orders.path=/v2/orders`，缺少 `sync.targetPath`，当前生效路径为 `/v1/orders`。健康环境、只有凭据错误、只有下游不可用、未知版本或无法读取现场均不直接创建可批准的该动作。

最终配置通过确定性的变换生成：删除这次迁移的旧键并设置新键；其他无关配置保持不变，不能简单用只有一个键的 Map 覆盖整个配置。前置条件依赖真实字段，不依赖 `scenario=migration` 标签或模型判断。

预检查不写配置、不主动发送订单同步、不调用模型。可以使用只读健康检查辅助展示，但健康正常不代表业务凭据有效。知识与模型建议不能扩大目录中的动作参数。

### 4.2 冻结内容

提案快照至少包含：

| 分类 | 内容 |
| --- | --- |
| 身份 | schemaVersion、planId、actionId/actionVersion、targetId、instanceId |
| 前置条件 | 应用版本、环境 revision、提供配置与生效配置、必要的事实采集时间 |
| 变更 | 精确 before / after、配置变换摘要、影响及不回滚边界 |
| 验证 | 固定验证策略/版本、期望路径和响应结构、超时及最大调用次数 |
| 来源 | 可选 sourceRunId、关联证据 ID、提案理由与服务端创建人 |
| 时效 | createdAt、planExpiresAt、审批策略版本 |

使用确定性字段顺序和规范化 JSON 计算 `planHash`，不依赖普通 Map 迭代顺序；审批同时绑定 planId、planHash、动作/验证版本、实例和环境修订。摘要是内容绑定手段，不替代服务端权限。

审批身份、时间、批准截止时间均由服务端生成。客户端不能提交 `approvedBy`、`executedBy` 或任意绑定字段。执行前重新确认审批人和执行人仍具 ADMIN 权限；当前没有角色修改界面，也应保留该服务端检查。

### 4.3 环境修订与实例身份

- 每次应用启动生成新的 instanceId。旧进程的内存状态和回执不能跨启动继续使用。
- 配置或合成故障条件变化时单调增加环境 revision，包括切换到同名场景及旧人工操作；即使值变回原样也不能复活旧审批。
- 普通日志追加、只读健康查询和单独同步不增加配置 revision，但其请求 ID 不能混入修复回执。
- 对提供配置、生效配置和必要条件计算稳定指纹作为额外核验；不能只信网页传来的 revision。
- 动作应用在 `DemoEnvironment` 同一临界区中完成“核对 instance/revision/前置条件 → 修改 → 保存内存应用回执”，避免检查后再写的竞争。
- 执行后配置 revision 必须与应用回执一致；不能在验证前允许其他写入穿插。

## 5. 状态与执行事务

### 5.1 状态模型

提案状态建议为 `PENDING_APPROVAL → APPROVED → EXECUTING → FINISHED`；未执行时可转 `REJECTED`、`CANCELLED`、`EXPIRED`、`STALE`。拒绝、撤销、过期、失效和已执行提案不能再次批准或执行；重做意图创建新提案。

执行生命周期与事实分开保存：

| 字段 | 建议值 | 含义 |
| --- | --- | --- |
| applicationStatus | NOT_STARTED / NOT_APPLIED / APPLIED / UNKNOWN | 配置写入是否有确定证据 |
| verificationStatus | NOT_RUN / RUNNING / PASSED / FAILED / UNKNOWN | 本执行的新业务验证结果 |
| executionStatus | RUNNING / SUCCEEDED / FAILED / VERIFICATION_FAILED / UNKNOWN / CLOSED_UNRESOLVED | 对人员展示的综合状态 |

`SUCCEEDED` 必须是 APPLIED + PASSED。确定没有应用才可以标记对应的 NOT_APPLIED；连接异常、超时或进程中断不能自动解释为未应用。配置已应用而收到明确 401/503 或 `accepted!=true` 时为 VERIFICATION_FAILED，不回退为“未执行”。

正常终态不被迟到响应覆盖。UNKNOWN 只允许通过独立核查命令，在校验完整原操作证据后条件更新；保留原 UNKNOWN 事件和核查依据。人工结束未决记录为 CLOSED_UNRESOLVED，保留 UNKNOWN 事实，不能改成成功或失败。

### 5.2 一次执行的顺序

1. HTTP 层验证登录、ADMIN、来源和 POST 请求头。解析有界 DTO，拒绝额外可执行参数。
2. 先查询固定幂等请求；已有记录返回原执行，不因审批已消费而重复失败或再次写入。
3. 进入与诊断准入相同的 `RunService.whenIdle` 临界区。该临界区覆盖最终检查、受理、应用、验证和必要的收尾；网络调用仍在数据库事务之外。
4. **短事务 A**：锁定提案，校验版本、审批、有效期、身份和目标；按旧状态消费审批，建立唯一 executionId / operationId、固定验证请求 ID 和幂等请求记录，追加受理事件后提交。
5. 在示例适配器内再次原子核对实际实例与环境修订。验证不符时不应用，记录明确结果；不能按最新环境悄悄重算参数。
6. 应用确定的配置变换，生成带 operationId 的应用回执；按冻结策略发出最多一次新的订单同步请求，并读取对应响应和配置。
7. **短事务 B**：校验操作身份与当前状态，原子保存应用/验证证据、执行结论、完成时间和事件，再将提案完成。
8. 返回持久化的结果；如果终态保存失败，不向用户宣称落库成功。保留原请求身份，通过核查流程补录证据。

同步执行不创建持久化排队任务，不通过页面刷新恢复写入。HTTP 请求断开不意味着操作未开始；服务端保留在途身份，核查不得与仍在执行的处理器争抢完成状态。总执行预算建议 10 秒，各 HTTP 调用保留更短超时；超时不产生第二次业务 POST。

`whenIdle` 已是单进程同步准入，不应仅为了本功能重写整个诊断调度器。实现必须避免锁顺序反转，不持有数据库行锁等待网络，不让新的服务依赖形成环。

### 5.3 幂等协议

- 创建、审批/驳回、撤销、执行、核查及人工结束未决记录均携带 `requestId`；服务端以“操作者 + requestId”唯一约束，并绑定操作种类、目标和规范化请求摘要。
- 同编号、同请求返回原受理结果；同编号、不同目标/正文返回 409 `REMEDIATION_REQUEST_CONFLICT`。
- 每个提案最多一个审批决策、一个执行记录；多个不同 requestId 并发执行同一提案也只能产生一次应用和一次业务验证。
- 已创建 executionId 后不得通过新 requestId 再执行同一提案。执行编号、适配器 operationId 和业务验证请求编号分别保存并关联。
- UI 在发请求前保存完整 method/path/body/requestId；不在失败后重建正文或编号。GET 查询失败、暂时 404、页面刷新或退出重登都不解锁一个新的写请求。
- 确认未受理时也只能在仍有效的条件下重发原请求。已经持久化的拒绝结果应稳定返回；需要改变意图时由人员显式创建新请求。
- 本地恢复记录按账号隔离，禁止另一账号读取/重用；不保存 Cookie、密钥或来源全文。敏感理由尽量只存在服务端，执行类请求正文只含引用和固定标识。

## 6. 结果不明与恢复

| 故障位置 | 要求 |
| --- | --- |
| 受理事务提交前失败 | 没有外部写入；固定请求可以查证并按原样重试 |
| 受理已提交，应用尚未开始 | 不自动接续写入；同实例通过可信适配器回执确认未应用，不能仅凭无结果行推定 |
| 应用后终态保存失败 | 同实例读取原 operationId 的回执、原请求响应并补录，不重新应用 |
| 验证 POST 响应不明 | 保存 APPLIED（若有回执）和 verification UNKNOWN；不把新发请求当成原验证结果 |
| 浏览器丢失响应 | 按原 requestId 查询，继续展示原执行；禁止另开执行 |
| JVM 重启 | 未执行旧提案失效；旧 RUNNING 记录转待核查。新 instanceId 不能接续旧操作 |
| 重启后内存回执丢失 | 保留 UNKNOWN；即使新实例默认配置不同，也不能反推旧操作结果 |
| 环境当前看起来正常 | 只能作为“当前观察”；没有原操作回执与关联业务响应时不能确认本次成功 |

受控适配器应维护有界的本实例回执缓存和在途登记，记录应用前后 revision、固定验证请求与响应。受理前预留容量，容量不足时拒绝新的执行；不能驱逐仍在途或待补录操作。已完整持久化的终态回执可回收。缓存非持久化，不能声称跨进程恰好一次。

执行记录保留所属 instanceId 和足以区分 PID 复用的进程启动身份。启动恢复须核对旧执行所属进程；无法确认退出时保持待核查，不抢占、不将“超过时间”直接当作进程已死。V1 不支持两个实例共享同一可变目标的并行操作，不能因存在数据库状态字段而宣称已有分布式执行保证。

UNKNOWN 的核查证据不足时保持原状态。人工可说明原因结束未决记录，但仅限已确认原处理器退出的执行；仍在途时拒绝。之后若需要重试业务意图，应重新采集现场、创建提案并审批。旧记录不被清除，新记录关联 `supersedesExecutionId`。

同一实例同一目标有待核查执行时阻止新修复，直到完成证据核查或人工结束；新实例也应先提示并处理该目标的历史未决记录。场景重置不能抹掉未决记录或自动完成它。

## 7. 验证与证据契约

一次修复验证通过必须同时具备：

1. 应用回执证明本 operationId 将冻结的 before 改为 after，实例、动作版本和 revision 一致。
2. 配置读回的 `sync.targetPath` 为 `/v2/orders`，其他配置按提案保留。
3. 在应用之后创建的独立业务请求访问固定本地下游路径，关联本 executionId 的 requestId。
4. 下游 HTTP 200，结构化响应 `accepted=true`；空正文、无法解析、只有健康检查 200 均不算通过。
5. 所有证据已原子落库，且没有目标变化或时间顺序矛盾。

记录采集时间和服务端顺序，不仅靠字符串时间比较。保存脱敏配置差异、应用回执、请求 ID/路径、HTTP 状态、结构化响应、错误码和状态转换；不保存 Authorization 或凭据。历史资料、诊断答案及备注按不可信文本渲染。

修复报告包含动作/审批/验证版本、planHash、参与人、全部阶段状态与时间、原始证据引用、核查记录、环境重启说明和人工处理边界。未决记录导出必须保持未决，不能因人工关闭统计为成功。

## 8. 模块、数据与接口

### 8.1 分层与依赖

新增 `io.supportops.remediation`，按 controller / service / service.impl / dto / vo / entity / mapper / constant 分层；XML 放 `mapper/remediation/`。固定动作注册与适配器可以采用配置组件或内部类，不机械增加空接口。

依赖方向：RemediationController → RemediationService → Mapper；RemediationService 经 DemoService 或明确的 DemoRemediationAdapter 获取目标能力，经 RunService 使用准入/读取诊断，经 UserService 查询有效身份。不得直接读取 agent/user 模块 Mapper。

内部 adapter 契约表达 preview、applyOnce、verifyOnce、inspectReceipt，使用明确 DTO；同一 operationId 不重复产生动作。HTTP 层、前端和模型均不能直接调用 apply。MCP 与 Skills 不新增写入入口。

### 8.2 建议持久化模型

| 表 | 主要内容与约束 |
| --- | --- |
| `remediation_plans` | 不可变内容快照、planHash、目标/实例/修订、来源诊断、创建人、状态、版本、有效期；分页索引 |
| `remediation_decisions` | 每 plan 唯一的批准/驳回决策，绑定 hash、操作者、策略、时间和截止时间；撤销通过提案状态和事件记录 |
| `remediation_executions` | 每 plan 唯一；operationId 唯一；应用/验证/综合状态、请求关联、证据、错误、核查版本及前次执行引用 |
| `remediation_requests` | 操作者 + requestId 唯一；操作种类、请求摘要、受理状态和结果引用；防止响应丢失时另建命令 |
| `remediation_events` | 追加式事件、计划/执行关联、操作者、目标、顺序、时间、固定类型和有界载荷；记录核查与必要的示例重置操作 |

事件载荷可以采用带 type/schemaVersion 的受控 JSON；稳定业务字段使用 DTO/VO，不把全部模型藏在 Map 中。字段长度、配置快照/报告大小上限必须明确，建议单提案公开快照不超过 64 KiB、单执行证据不超过 256 KiB。提案超限在应用前拒绝；执行后发现证据超限时仍保存操作身份、已知阶段事实、证据不完整标记与错误码，无法证明的部分保持 UNKNOWN，不静默截断后标为通过。报告总量达到上限时明确报错，不下载半份成功报告。

创建、决策、执行受理、完成及核查各自使用短事务；状态变化和对应审计同事务提交。外键 ID/字符集沿用现有用户和诊断表；可空关联不能伪造系统用户。示例场景操作事件可以没有 planId，但必须保留目标与操作者。

V9（实施时核对）只增加表和必要兼容列，不清空数据。验证空库 B3→最新，以及已有 V8 含评测/审阅/事件数据后的升级。现有 `EvaluationMigrationTest` 对迁移次数有固定断言，需要按实际新增迁移更新，保留历史内容一致性和表结构断言。

### 8.3 API 规划

全部仅 ADMIN；查询 GET，命令 POST，沿用统一错误结构、Cookie、来源检查和 `X-SupportOps-Request: 1`。

| 方法与路径 | 用途 |
| --- | --- |
| GET `/api/remediations/actions` | 固定动作目录与当前可用性 |
| POST `/api/remediations/preview` | 有界只读预检查；不创建执行、不发送业务 POST |
| POST `/api/remediations` | 重新核对现场并创建不可变提案，不能信任网页传回的快照 |
| GET `/api/remediations` | 分页筛选 |
| GET `/api/remediations/{id}` | 提案、决策、执行及能力状态 |
| POST `/api/remediations/{id}/approve` | 审批，绑定 expectedVersion / planHash / requestId |
| POST `/api/remediations/{id}/reject` | 驳回，说明原因 |
| POST `/api/remediations/{id}/cancel` | 撤销未执行提案；与执行受理竞争只允许一方成功 |
| POST `/api/remediations/{id}/execute` | 消费审批并同步执行，响应返回持久化结果 |
| GET `/api/remediations/requests/{requestId}` | 查询当前操作者的原请求受理结果 |
| GET `/api/remediations/{id}/events` | 有界按游标读取审计 |
| POST `/api/remediations/executions/{id}/reconcile` | 只核查原回执，落库核查记录，无新的修复或业务 POST |
| POST `/api/remediations/executions/{id}/close-unknown` | 确认原执行已退出后人工结束未决记录，要求理由 |
| GET `/api/remediations/{id}/report` | JSON / Markdown 报告，白名单 format |

预检查虽只读，但用 POST 承载结构化输入；不得造成业务副作用。状态/版本冲突、审批失效、目标变化、动作不适用、请求冲突、未决执行阻断均用可区分的稳定错误码。401/403 沿用认证授权；404 不泄露他人请求编号；读接口不能触发业务验证或修复。

服务端启动时只完成保守状态恢复，不执行动作。前端所需 `canApprove/canExecute/canReconcile` 可由服务端给出，但命令仍独立重新校验，不能把 UI 状态当权限。

## 9. 前端恢复与可用性

- 与现有管理页面风格一致；概览、审批、执行证据、审计分区，不用原始 JSON 作为唯一界面。
- 用明确文案区分“批准修复”和“执行已批准修复”，展示具体差异及过期时间。
- 页面刷新后从服务端恢复提案状态；仅有未决请求时低频查询，不改动诊断 SSE。
- pending 命令持久化到账号隔离的本地记录；提交失败时保留冻结请求，退出登录不得泄露给另一账号。
- 409 保留当前表单和待核查身份，先展示服务器状态；禁止重新生成请求编号绕过冲突。
- 来源诊断、配置、错误、理由、报告均按文本/安全 Markdown 展示，防止注入。
- 弹窗有焦点管理、键盘可达及状态播报；窄屏可读差异与审批内容。
- `/api/demo/repair-config` 和新执行接口共用同一幂等/审批服务，重复从两个入口提交也不会重复应用。
