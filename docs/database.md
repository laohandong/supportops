# 数据库维护

## 拆分后的数据归属

SupportOps 保留 B3 至 V15 与旧 14 张评测表。V16 加入来源和迁移控制，V17 建立旧表写门禁，V18 补注释，V19 绑定唯一迁移目标代次。外部评测项目使用自己的数据库及迁移历史，不复制源 Flyway 控制表。以下旧版本说明用于历史维护，当前边界见[协作说明](evaluation-split.md)。

## 专属部署的停写备份与恢复

可靠性工具对已登记的单机独占 Compose 部署执行完整备份：主业务库、Excel 动态库、MinIO 原件、Elasticsearch 官方快照、程序及受限本地配置必须配套保存。当前格式为 `SUPPORTOPS_BACKUP_V2`；旧整体格式仅通过显式 `restore-legacy` 入口恢复。默认生成只读计划，执行阶段再次绑定部署 UUID；不接受未知或仍活动的应用、后台任务及数据库写入连接。精确命令、维护锁、权限和规模限制见 [运行身份、只读检查与停写恢复](reliability-delivery.md)。

恢复只创建全新目录、端口、容器与卷，全部文件和版本校验发生在目标写入前。失败目标保留 `PARTIAL`，不得继续追加或启动；重新演练使用另一个新目标。恢复后重新核对两库所有行、列类型、索引、约束、字符集、排序规则、原件及索引内容。原始配置封存，外部模型、飞书和后台消费者默认关闭。此工具不覆盖日常工作台、共享服务器、在线备份或跨版本升级；已有迁移文件保持不变。

## V6 / V7 / V8 评测中心升级

新增 `V6__evaluation_center.sql`，在 B3、V4、V5 后增加十张独立表：评测集、案例、实验、尝试、组、样本、证据、审阅、事件、执行器守卫。`V7__evaluation_descriptions.sql` 为这些表补全中文表/字段说明，保留类型、空值、默认值与索引。`V8__evaluation_recovery_evidence.sql` 为尝试增加原执行令牌、独立补录状态/错误、封存事件 SHA-256/字节数五列。空库顺序应用 B3 → V4 → V5 → V6 → V7 → V8；已有数据库只应用尚未执行的增量迁移。升级前按本页备份实际目标；不清库、不改写旧迁移。

V8 不改写旧事件、样本、证据或审阅。未中断的已领取尝试回填原执行令牌；升级前已经提升令牌的中断尝试不猜测旧值，只有在确认全部关联进程退出并核对受限原清单后才能补录。无法核实则保留守卫与独立错误。已经删除原材料的旧记录不能从不存在的文件补救；原有已入库证据仍可读取。

用户关联沿用现有 UUID 与 `utf8mb4_bin`。策略/重复、样本/案例、事件序号、证据顺序与审阅修订有唯一约束，关联有外键；执行器守卫预置单行。启动与证据导入使用短事务及旧状态/版本条件更新。来源、模型与临时资源保存在评测域，已有诊断、上传和飞书表不改写。本轮真实 V5 升级和旧记录读取的具体证据见 [验证结果](validation.md)。

## 首次使用与自动初始化

新用户按 [本地部署与启动依赖](deployment.md) 启动即可。应用通过内置 Flyway 自动创建业务表、索引和初始化锁记录；不预置管理员或登录密码，无需手动执行 SQL，也无需额外安装 Flyway 命令行工具或服务。

Flyway 随 Java 应用运行，用于记录已应用的结构版本、校验迁移文件并执行后续增量。当前空库依次执行 B3 全量基线及 V4–V19 增量迁移；正常重启不会重复建表。MyBatis-Plus 负责业务数据访问，Flyway 负责表结构，两者职责不同。

| 使用情况 | 处理方式 |
| --- | --- |
| 新用户、空业务库 | 使用默认配置启动，由应用自动初始化 |
| 已由当前 B3 管理的版本 3 库 | 备份并核对连接后启动，自动应用 V4–V19 |
| 已完成 B3 / V4 的库 | 备份并核对连接后启动，自动应用 V5–V19，不改写既有记录 |
| 已完成 V5–V18 中某一版本的库 | 启动时校验历史，仅应用尚未执行的后续迁移直至 V19 |
| 已完成 V19 的库 | 校验全部历史及摘要，不重复执行已完成迁移 |
| 已完整执行已移除的旧 V1–V3 文件 | 按本文“已有 MySQL 数据库接管”核对结构与历史后接管 |
| 旧 H2 文件 | 使用本文显式离线迁移入口 |

后续结构变更新增高于已发布版本的迁移文件；已应用的 B3 与 V4–V19 不改写、不合并。V5 曾增加飞书绑定、收件和回复三张表；19 张业务表、190 个字段是 V5 的历史结构，不是当前结构。本文以下步骤面向已有数据或手动维护场景。

## 手动初始化空业务库

手动导入 B3 后以版本 3 建立基线，再由应用依次执行 [迁移目录](../src/main/resources/db/migration) 中的 V4–V19。归档、飞书、历史评测、受控修复、处理结果、企业接入与拆分写保护均通过增量建立。原记录默认未归档。不要将仅导入 B3 的库标记为任何尚未执行的增量版本。已有旧 V1–V3 库使用下一节的接管步骤，不重复导入全量脚本。

[`src/main/resources/db/migration/B3__supportops_initial.sql`](../src/main/resources/db/migration/B3__supportops_initial.sql) 是唯一的 MySQL 8.4 业务初始化脚本，以 Flyway 全量基线版本 3 管理，包含 16 张表、158 个字段、索引、外键、角色约束及首次管理员创建所需的固定锁记录。表和字段使用中文 `COMMENT`，可由数据库客户端直接查看。脚本不创建默认管理员，管理员仍通过首次启动页面创建。

数据库与账号权限由部署环境准备；[mysql-init.sql](../infrastructure/mysql-init.sql) 仅负责本地建库和授权，不包含业务表。Excel 物理表按上传的 Sheet 动态创建，不属于固定初始化结构。原 V1–V3 及旧 H2 建表文件已移除，H2 离线工具直接读取已有数据库。

1. 准备空业务数据库，确认连接指向该库。脚本不包含 `DROP TABLE` 或 `IF NOT EXISTS`，遇到同名表会报错；不要对已有业务库或导入失败的半成品库重复执行，也不要让客户端忽略错误继续导入。MySQL DDL 不支持整份脚本的事务回滚。
2. 使用 UTF-8 客户端导入。以下命令在 MySQL 客户端执行，`supportops` 替换为实际空库名称，路径替换为本机仓库绝对路径；Windows 客户端可使用正斜杠路径：

   ```sql
   USE supportops;
   SOURCE /path/to/SupportOps/src/main/resources/db/migration/B3__supportops_initial.sql;
   ```

3. 确认导入完整成功后，首次启动应用时显式设置 Flyway 基线版本为 `3`，让 Flyway 接管这个已经具有 V3 结构的数据库。PowerShell 示例：

   ```powershell
   $env:SPRING_FLYWAY_BASELINE_ON_MIGRATE='true'
   $env:SPRING_FLYWAY_BASELINE_VERSION='3'
   node scripts/start.mjs
   ```

4. 首次启动成功、Flyway 已建立基线后，移除这两个临时环境变量；后续启动保留默认 Flyway 校验和迁移行为。不要在全局配置中长期开启自动基线，也不要对未知结构的非空库设置版本 3 基线。

### 已有 MySQL 数据库接管

全量脚本不会给已有表补注释，也不能直接用于升级未完成旧迁移的数据库。已经完整执行旧 V1–V3 的数据库，其 Flyway 历史仍记录了已删除的迁移文件；直接使用新代码启动会因缺失旧迁移而校验失败。

接管前停止应用并备份，核实业务结构已完整达到版本 3、没有失败迁移或结构漂移。保留原迁移历史表的独立备份，并将其重命名为明确的审计表名；使用相同版本 Flyway 和当前 `db/migration` 路径，显式执行版本 `3` 的 `baseline`，再执行 `migrate`。默认迁移校验保持开启，新历史表应包含版本 3 的 BASELINE 以及 V4–V19 的成功记录，原业务表不重建。

不要仅对旧 V1–V3 执行 `repair` 后直接迁移：当旧迁移全部被标记为删除时，Flyway 可能把迁移状态视为空库，并尝试执行 B3 建表，遇到已有表失败。若已出现该情况，应先核对失败语句、现有结构和数据摘要，再保存该迁移历史并按上述基线接管；不能直接反复重跑、关闭校验或清空业务库。

尚未达到版本 3 的旧库需要根据实际差异制定升级 SQL，不能通过直接设定版本号跳过结构变更。当前已包含 V19，后续结构变更使用高于已发布版本 19 的新迁移，不改写任何已应用文件。

## H2 离线迁移

旧 H2 不会在新版本启动时自动改写。迁移工具只读取明确指定的 H2 文件，并要求 MySQL 目标业务表为空；业务数据复制及文档结构转换在同一目标事务中提交。源文件不存在、目标非空或复制失败均停止，不通过清空数据解决。

1. 停止旧工作台及准备连接目标库的新工作台，备份旧 `.mv.db` 文件和本地模型设置。
2. 创建空 MySQL 目标数据库及权限，准备新的已构建 JAR。不要预先向该目标导入示例资料。
3. 显式设置连接参数并运行迁移。H2 地址不带 `.mv.db` 扩展名，工具追加只读与 IFEXISTS 选项。

```powershell
$env:JAVA_HOME='你的 JDK 21 目录'
$env:SUPPORTOPS_MIGRATION_H2_URL='jdbc:h2:file:E:/backup/supportops'
$env:SUPPORTOPS_DB_URL='jdbc:mysql://127.0.0.1:13306/supportops?useUnicode=true&characterEncoding=UTF-8&serverTimezone=UTC'
$env:SUPPORTOPS_DB_USER='supportops'
$env:SUPPORTOPS_DB_PASSWORD='目标数据库口令'
node scripts/migrate-h2.mjs
```

脚本也读取 `.local/model.env`，非空文件值优先于进程环境，运行前核对其中目标连接。输出各旧表的复制行数。保留原文档/分片 ID、记忆、诊断、事件、自增事件号及已记录的用量；旧向量不当作 ES 可用索引，转换后创建关键词任务，启动新工作台再自动生成 ES 索引与向量。

旧版本没有留存的原件标记 `MISSING`，分片和历史证据仍可核对。页面允许补传 SHA-256 完全一致的原件；不同内容应上传新修订。确认迁移数量、历史问答、分片内容及索引任务状态后，保留源备份再启用新工作台。离线迁移不会自动停止操作者的进程。

迁移验证应核对源备份、行数、ID、历史问答、用量与索引发布状态。相关测试使用独立数据库，见 [验证结果与范围](validation.md)；当前账号与历史归属规则见 [用户系统](users.md)。

## V9 受控修复增量升级

`V9__controlled_remediation.sql` 仅增加 plans、decisions、executions、requests、events 五类 `remediation_` 表。提案一决定、一执行，操作UUID和验证请求UUID唯一，操作者+requestId唯一，并用外键关联账号与可选来源诊断。V8→V9 保留诊断、事件、账号、评测和审阅，不改写已应用迁移，也不清空数据。受理/完成及审计在对应短事务原子提交。升级前备份并核对活动任务，日常部署与隔离验收分别执行。见 [存储与边界](controlled-remediation.md#存储部署与边界)。

## V10 场景变更审计升级

`V10__demo_environment_audit.sql` 只新增 `demo_environment_events`，允许无关联提案的人工场景切换和重置保留历史。字段包括服务端操作账号、固定目标、原实例、前后修订、时间、脱敏事实和结果；账号外键及目标游标索引保持查询和归属约束。既有V9数据库只应用V10，不能修改V9校验和或清除修复、诊断、评测和审阅记录。意图和结果分别用短事务保存，网络在事务外；结果保存失败保留原STARTED记录，重启不会自动重复操作。

## V11 处理结果与案例库升级

`V11__diagnosis_outcomes_and_case_library.sql` 增加七张表：`diagnosis_outcomes`、`diagnosis_outcome_revisions`、`diagnosis_outcome_requests`、`evaluation_case_entries`、`evaluation_case_revisions`、`evaluation_case_events`、`evaluation_library_requests`，并为 `evaluation_cases` 增加可空外键 `library_revision_id`。旧内置案例保持 NULL，不生成虚构的发布来源。空库依次应用B3、V4～V11；已有V10库仅应用V11，先前迁移文件及校验和不改写。

结果按来源轮次唯一，修订按父记录/修订号唯一；案例按来源轮次唯一，发布按条目/修订号唯一；固定请求按操作者/编号唯一。UUID、UTC字符串、内容摘要和 utf8mb4_bin 关系保持现有语义。所有者、确认人、审计人与原请求操作者通过服务端账号关联。

保存及审计由服务短事务原子提交，业务拒绝通过保存点回滚本次业务变更并保存终局拒绝回执。请求、来源轮次/结果、案例、数据集采用统一锁顺序；最新来源使用加锁当前读，避免 REPEATABLE_READ 下旧快照参与并发发布。模型、嵌入和业务验证请求不进入这些事务。

升级前核对活动任务、实际JAR与数据库并停写备份；本开发包不自动升级日常工作台。现有完整停写备份按全库表结构与全部行采集，包含七张新表、外键、修订、发布历史、审计、原回执和历史评测证据，不依赖旧表白名单。恢复到全新隔离目标后先核对摘要，再启动指定新程序；旧审批仍转 STALE，UNKNOWN 不重放。MySQL DDL不保证整文件回滚，失败应核查真实结构及Flyway记录，不能清库或重写已应用迁移。

## V19 评测迁移目标绑定

`V19__evaluation_target_binding.sql` 只向 `evaluation_migration_control` 增加可空的 `active_target_generation`。已有业务表、主键、历史 JSON 和 B3、V4–V18 的校验和不变。AgentEval 离线切换先将来源绑定到唯一目标部署代次，再开放该目标；另一份同包副本不能启用。仅在确认目标无增量并冻结后，安全回退才会清除绑定并恢复源端写入。

新离线工具的冻结和切换要求源端具有 V19 结构；旧结构返回明确升级错误。该迁移已纳入隔离升级验证，当前工作台升级与业务切换属于单独的部署范围，不由开发验证自动执行。操作步骤见 AgentEval 的迁移手册。
