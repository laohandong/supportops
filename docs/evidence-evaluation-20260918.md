## 问题与修改

上一轮已经补全业务恢复验证，但日志查询失败时，部分回答仍把当前配置与文档规则改写成“同步模块实际使用某路径”或“配置导致本次失败”。正文另有日志缺失说明，不能消除摘要、标题或结尾中的确定性断言。

本次运行规则要求：

- 分列本次工具观测、适用文档规则与待验证推断。已配置凭据只证明配置状态，健康端点成功只证明该端点的结果。
- 缺少失败请求证据时，摘要与结尾保留配置差异、来源缺口及下一步；候选原因用条件关系说明，标题也明确其与本次失败的关联待验证。
- 已有真实请求日志支持的判断保留确定性，同时说明证据未覆盖的影响范围。不将所有结论一律降为猜测。
- 保留上一版有来源的业务恢复检查，不因健康检查正常或配置正确而宣称恢复。

评测报告按原顺序展示 `get_app_info`、`get_effective_config`、`get_recent_logs`、`get_downstream_health` 的调用与结果，包括事件 ID、调用 ID、状态和原文。来源报错、空结果与缺少返回分别保留；日志中的 Markdown 放入动态长度代码围栏。新增审阅维度不会自动判定自然语言质量，原始 `modelQualityVerdict=NOT_EVALUATED` 保持不变。

修改未新增工具、扩大权限或改变接口、数据库与检索预算；没有把示例的固定路径、响应码或答案写入运行提示词。模型对规则的遵守仍依赖生成行为，没有新增服务端语义拦截。
